AI 编程工具越来越多，值得比较的不只是“哪个模型写代码更强”，还有工具如何组织模型、上下文和执行过程。

[Pi](https://pi.dev/) 是其中一个很有特点的项目。它强调保持内核精简，让使用者能够按自己的习惯扩展工作流。**2026 年 10 月 1 日，Earendil 正式发布了 Pi 1.0。** [官方发布说明](https://earendil.com/posts/pi-1-0/)

这篇文章以截至 2026 年 10 月 8 日的官方资料为依据，介绍 Pi，并与 Claude Code、Codex 对比。它是产品设计与工作流分析，不是三款工具的实测性能排名。

## Pi 是什么？先分清模型和工具

Pi 是一个可以在终端使用、也可以嵌入应用的 agent harness。这里的 harness，可以理解为组织模型调用、工具执行、上下文和会话的运行框架。[Pi 文档](https://pi.dev/docs/latest)

模型负责理解任务与生成下一步动作，运行框架负责把这些动作接到文件、命令和真实工作环境中。

因此，讨论 Pi 时要区分两个问题：所连接的模型是否适合任务，以及 Pi 的工作流是否符合自己的习惯。换模型可能影响代码质量，换运行框架则可能改变上下文组织、交互和执行方式。

Pi 支持多家模型提供方，也允许通过扩展、Skills、提示词模板和主题定制体验。会话可以按树形结构回到先前节点继续探索；自动化入口包括 print/JSON、RPC 和 SDK。[Pi 官网](https://pi.dev/)

这些能力适合一种需求：希望保留同一套工作习惯，同时选择不同模型，并逐步加入自己的工具。

## Pi 1.0 更新了什么

这次发布值得关注的变化包括：

- Codemode：原生 MCP 支持，也能接入 Jev 等非语言模型能力。
- 虚拟模型扩展：为自定义模型路由提供扩展入口。
- 延迟加载工具：调整工具进入上下文的方式。
- Anthropic 模型缓存预热，以及对话中途的系统消息变化支持。
- 新终端主题，默认全屏模式。

这些更新来自 [Pi 1.0 发布说明](https://earendil.com/posts/pi-1-0/)。

这里需要纠正一个容易沿用的旧印象：**Pi 1.0 已经内置 MCP 和 Codemode。** “Pi 不支持 MCP”已经不适合作为当前版本的介绍。[Pi 官网说明](https://pi.dev/)

我关注的是工具和模型组合的空间变大了。接入一个能力后，下一步还可以思考：什么时候调用它、结果如何进入后续动作，以及是否值得把这套策略做成可复用扩展。

## Pi Durable：同期发布，但需要单独理解

Pi 1.0 同期发布了 **Pi Durable**，它是独立的实验性包，不应把它的所有能力直接当作终端 Pi 的默认功能。[发布说明](https://earendil.com/posts/pi-1-0/)

Pi Durable 面向长期运行的 agent 应用，通过任务检查点和持久化存储恢复中断的运行。中断的工具调用如何处理，取决于是否能安全重试；它不是对任何外部操作都保证“重跑一次没有副作用”。[Pi Durable 技术介绍](https://earendil.com/posts/pi-durable/)

对应用开发者来说，这涉及一个不同层次的问题：除了让 agent 完成任务，还要处理进程退出、重复提交、任务恢复和外部操作的幂等性。

普通终端使用可以先从 Pi 开始。只有在设计持续运行的服务时，再评估 Durable 是否解决了自己的具体问题。

## 对比 Claude Code 和 Codex

三者都能参与代码工作，但默认工作流和扩展重心有所不同。下面先比较入口和机制，再讨论选择。

| 维度         | Pi                                   | Claude Code                            | Codex                                     |
| ------------ | ------------------------------------ | -------------------------------------- | ----------------------------------------- |
| 主要特点     | 精简内核，强调自定义运行流程         | 围绕 Claude 的编程工作流与开发工具集成 | OpenAI 编程代理，连接本地、IDE 与云端工作 |
| 使用入口     | 终端；print/JSON、RPC、SDK           | 终端、IDE、桌面与浏览器                | CLI、IDE 扩展、桌面与云端                 |
| 扩展方式     | 扩展、Skills、模板、主题、Packages   | Skills、插件、Hooks、MCP 等            | Skills、插件、MCP 等                      |
| 复杂任务组织 | 子代理和计划模式主要通过扩展或包实现 | 提供子代理等工作流能力                 | 提供子代理、审查和云端任务入口            |
| 需要重点评估 | 自定义流程的开发与维护成本           | 已有 Claude 工作流是否匹配项目         | 本地与云端的任务组织是否匹配项目          |

表格中的产品能力依据 [Pi 官网](https://pi.dev/)、[Claude Code 官方概览](https://code.claude.com/docs/en/overview)和 [Codex CLI 官方文档](https://learn.chatgpt.com/docs/codex/cli)。最后一行是我的选型分析。

### Pi：愿意自己塑造工具的人会更感兴趣

Pi 的吸引力在于可以按自己的方式组装工作流程。官网明确说明，子代理、计划模式等能力并不是默认内置的固定流程，可以自行扩展或安装相应包。[Pi 官网](https://pi.dev/)

这适合喜欢研究工具机制的人：例如定义一个命令、接入内部接口，或给不同任务阶段选择不同模型。

代价是配置和维护也由自己承担。扩展越多，越需要关注版本兼容和团队成员能否复用同一套设置。

### Claude Code：关注现成的 Claude 开发工作流

Claude Code 能读代码、改文件、执行命令，并与开发工具集成。它提供终端、IDE、桌面和浏览器入口，也支持持久指令与子代理等能力。[Claude Code 官方概览](https://code.claude.com/docs/en/overview)

如果团队已经围绕 Claude 建立习惯，选择它可以减少重新组织流程的工作。这里说的是工作方式匹配，不代表它在所有代码任务上的结果都优于其他工具。

它同样可以定制；“Pi 更强调可塑性”不意味着 Claude Code 没有扩展机制。

### Codex：关注本地执行、审查与云端协作

Codex CLI 支持本地代码探索、修改、命令执行和 `codex exec` 自动化，也提供审查、Skills、插件、MCP、子代理及云端任务入口。执行边界可以通过权限设置检查和调整。[Codex CLI 官方文档](https://learn.chatgpt.com/docs/codex/cli)

如果任务经常在本地修改、代码审查和云端处理之间切换，这些入口值得一起评估。

Codex 也不只是一条终端命令。比较时应说明使用的是哪个入口，避免把某个客户端的体验当作整个产品的能力边界。

## 使用前还要考虑执行边界

Pi 的项目信任机制决定加载哪些项目资源，但不会把工具调用自动变成沙箱执行。工具和扩展按 Pi 进程的权限运行。[Pi 官方文档](https://pi.dev/docs/latest)

因此，如果要运行第三方扩展或无人值守任务，除了“能不能调用”，还需要决定它应该在哪个环境中执行。

这种选择不能只看工具是否弹出确认框。还要看可写目录、网络访问、凭据暴露，以及操作出错后如何恢复。对三款工具都应该检查实际配置，而不是凭默认印象判断。
